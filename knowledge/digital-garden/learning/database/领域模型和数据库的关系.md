# 从数据库到产品：理解领域设计（Domain Design）

> 学习 FastAPI 之后，我发现真正困难的不是写 API，而是决定：
> 
> **这个世界里的东西，到底应该如何被表示。**

这就是领域设计。

---

# 1. 什么是领域设计？

简单理解：

> 领域设计 = 把现实世界中的事物和关系，转换成软件可以理解的模型。

不是一开始设计数据库。

而是：

```
现实世界

↓

领域模型

↓

数据库模型

↓

代码实现
```

---

# 2. Entity（实体）是什么？

实体：

> 可以独立存在，并且拥有自己生命周期的对象。

例如 It Grows：

```
🌱 Knowledge

📁 Project

🤖 Agent

💬 Conversation
```

它们都可以：

- 创建
    
- 修改
    
- 删除
    

所以它们是实体。

---

# 3. 属性（Attribute）是什么？

属性：

> 描述实体的信息。

例如：

```
Knowledge

├── title
├── content
├── created_at
└── updated_at
```

这里：

Knowledge 是实体。

title、content 是属性。

---

# 4. 为什么不要直接从数据库开始设计？

错误思路：

```
我要建一张表

↓

随便加字段
```

容易变成：

```
Knowledge

title

content

tag1

tag2

project_name

category_name
```

问题：

信息重复。

关系混乱。

未来难以扩展。

---

正确思路：

先思考：

```
世界里有哪些东西？

↓

它们有什么关系？
```

# 6. 主键（Primary Key）

每个实体都需要唯一身份。

例如：

```
Knowledge

id = 001
```

为什么不用标题？

因为：

标题可以修改。

ID 不应该改变。

---

# 7. 外键（Foreign Key）

外键表示：

实体之间的关系。

例如：

```
Project

id = 1


Knowledge

id = 100

project_id = 1
```

表示：

这篇 Knowledge 属于这个 Project。

---

# 8. 一对多（One To Many）

例如：

一个 Project：

可以拥有很多 Knowledge。

```
Project

   │

   ├── Knowledge A

   ├── Knowledge B

   └── Knowledge C
```

关系：

```
1 : N
```

---

# 9. 多对多（Many To Many）

例如：

Knowledge 和 Tag。

一篇知识：

可以有多个标签。

一个标签：

也可以属于多个知识。

```
Knowledge

     ↕

    Tag
```

数据库中通常需要中间表：

```
KnowledgeTag
```

---

# 10. It Grows 的未来方向

随着产品成长：

```
Knowledge

↓

Chunk

↓

Embedding

↓

AI Retrieval
```

未来：

AI 不只是读取文章。

而是理解整个知识网络。

---

# 最后的理解

以前：

我认为数据库设计就是：

> 建表 + 设置字段。

现在：

我认为：

> 数据库只是现实世界建模后的结果。

真正重要的是：

1. 找到实体
    
2. 分析实体关系
    
3. 决定数据如何流动
    

---

## 对 AI Agent 开发的意义

未来开发 AI Agent：

真正困难的不是调用模型 API。

而是：

设计：

- Agent 的身份
    
- Memory 的结构
    
- Knowledge 的组织方式
    
- Conversation 的生命周期
    

优秀的 AI 产品，本质上都是优秀的数据世界设计。

而 It Grows 的目标：

就是让个人知识、项目、AI Agent 在同一个生态中持续成长。🌱
