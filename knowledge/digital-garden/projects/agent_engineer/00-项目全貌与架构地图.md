# 项目全貌与架构地图

## 这个项目做了什么

一个带 Agent 色彩的个人博客网站：

```text
写文章 → 存进 PostgreSQL → Markdown 渲染到首页
   ↓
把笔记放进 knowledge/ → RAG 检索 → AI 助理带着出处回答
   ↓
登录用户 → JWT → 才能写文章、删除文章、调用助理
   ↓
异步任务 → 摘要任务入队 → Worker 轮询执行 → 查询状态
```

## 30 秒版本

> 我做了一个个人 AI Agent 博客。前端是 Vue 3 + TypeScript，后端是 FastAPI 分层架构，
> 包含 JWT 登录、Markdown 发布、RAG 笔记问答、流式 AI 助理和异步任务引擎。
> 前端部署在 GitHub Pages，API 部署在 Render，数据库用 Neon PostgreSQL。

## 2 分钟版本

按这个顺序讲，不要跳：

```text
1. 业务闭环：写文章 → 建知识库 → 问答 → 助理带出处回答
2. 分层架构：Router → Service → Core / Model / Schema
3. 安全：bcrypt 存密码哈希，JWT 做无状态登录
4. RAG：knowledge/ 笔记 → 切块 → jieba 分词 → 倒排索引 → Top-K
5. 流式：SSE/NDJSON，前端打字机效果
6. 异步：数据库任务表 + asyncio Worker
7. 部署：GitHub Actions 构建前端，Render 跑 API，Neon 存数据
```

## 目录逐层翻译

```text
backend/app/
  core/     基础设施：config、database、security、llm、rag、task_engine
  models/   数据库表模型：User、Post、Task
  schemas/  请求/响应数据契约：BlogPostCreate、UserLogin、AssistantRequest
  services/ 业务逻辑：认证、文章、RAG、助理、任务
  routers/  HTTP 入口：/api/auth、/api/posts、/api/rag、/api/assistant、/api/tasks
  tasks/    异步任务处理器：post.summarize
```

## 一次请求的生命周期

以“登录后写一篇文章”为例：

```text
浏览器点击发布
  → POST /api/posts 带 Authorization: Bearer <token>
  → Router 只做 HTTP 接收
  → get_current_user 验签，拿到当前用户
  → PostService 做业务：构造 Post、写库、刷新
  → 返回创建好的文章
  → 前端跳回首页，文章列表自动刷新
```

## 面试怎么讲架构

不要说“我用了分层架构”就结束。
要说出分层解决的是什么问题：

- Router 只关心 HTTP，不写业务。
- Service 是业务导演，知道什么时候调用谁。
- Core 是可复用的基础设施，和具体接口无关。
- Model 管数据库，Schema 管外部数据契约。
- 换数据库、换 LLM、加新业务，都只改对应的一层。

面试官真正想听的不是目录名，而是：

> 你为什么把代码放在这个位置？换一个需求，你改哪里？
