# 用户鉴权与前端会话

## 后端：双 Token 设计

用户登录返回：

```
access_token   → 短期（例如几十分钟），每个请求带着
refresh_token  → 长期，仅用于换新 access_token
```

`utils/jwt_tools.py` 负责签发和解码。解码时有个细节：

```python
payload = await decode_token(credentials.credentials, refresh_access_ttl=True)
```

这表示**每次使用 access token 时刷新它的有效时间**（滑动过期），用户只要活跃就不会突然掉线。

## 默认管理员

`ensure_default_admin()` 在启动时保证存在默认管理员账号。这是很多内部系统的常规做法：首次启动即可用，密码来自环境变量而不是写死。

## 前端：axios 双拦截器

```ts
// 请求拦截器：有 token 就带上
config.headers.Authorization = 'Bearer ' + localStorage.getItem('access_token')

// 响应拦截器：401 且没重试过 → 用 refresh_token 换新 → 重放原请求
```

三个容易忽略的细节：

### 1. `_retry` 防止死循环

```ts
originalConfig._retry = true
```

如果新 access token 还是 401，直接失败，不再重试。

### 2. 单飞（single-flight）刷新

```ts
let refreshTokenRequest: Promise<string> | null = null
```

多个请求同时 401 时，只发一次 refresh 请求，其他请求复用同一个 Promise。避免“十连 401 → 十次刷新”。

### 3. 登录接口不参与续期

```ts
const isAuthRoute = url => url.includes('/users/login') || url.includes('/users/refresh-token')
```

登录失败不能触发“刷新”逻辑，否则会循环。

## 路由守卫

```ts
router.beforeEach((to) => {
  if (to.path !== '/login' && !token) return '/login'
  if (to.path === '/login' && token) return '/project'
})
```

前端守卫只是 UX 优化，真正的安全边界永远在后端。

## 面试怎么答“Token 过期怎么办”

标准回答：

> “我们使用 access + refresh 双令牌。前端 axios 响应拦截器遇到 401 且请求未重试过，就用 refresh token 单飞刷新，拿到新 access token 后重放原请求；刷新失败就清空本地会话跳登录页。后端解码 access token 时会滑动续期，保证活跃用户不被踢下线。”

加分句：`_retry` 防循环、单飞 Promise 防并发刷新风暴、登录接口白名单。
