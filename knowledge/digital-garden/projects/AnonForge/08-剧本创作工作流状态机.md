# 剧本创作工作流状态机

## 为什么不能是“纯聊天”

如果 Agent 只是聊天，用户说“生成剧本”，模型随便输出一坨 Markdown，系统不知道：

```
创作配置确认了吗？
故事骨架生成了吗？
这次是生成还是重写？
输出有没有质量底线？
写坏了怎么回滚？
```

所以项目把对话升级成**状态机**。

## 会话状态：ScreenwritingSessionState

每个项目 + 用户有一个会话，持久化在数据库 `ScreenwritingSession` 的 JSON 字段里：

```
conversation_id    会话 ID
messages           对话历史
workspace          三个工作区全文
  skeleton / strategy / script
workflow           状态机字段
  projectConfig         创作配置
  basicInfoConfirmed    配置是否确认
  pendingStage          待执行的阶段
  completedStage        已完成阶段
  pendingScriptRepair   待确认的剧本修复
history             历史快照
```

## 单轮对话的处理流程

```
请求进来
  → 获取会话锁（同项目同用户串行）
  → 加载项目、状态、章节事件
  → 剧本修复确认状态机？（“确认重写 EP2？”）
  → 创作配置状态机？（草拟/修改/确认，规则驱动，零模型调用）
  → 解析阶段意图（“生成故事骨架”）
  → 构建 RAG 上下文
  → 构建 Agent（引导助理 or 阶段助理 or 团队）
  → 执行/流式输出
  → 提交对话 + 工作区
```

关键设计：**配置链路完全用确定性规则**（正则 + 关键词），不烧 token，不失控。

```
“剧本改成 8 集” → 规则解析 → 更新草稿 → “请确认？”
“确认”         → 规则识别 → 锁定配置
```

## 阶段生成：一次完整闭环

```
resolve_stage_generation(state, message)
  → 识别 stage + 检查前置阶段
  → 构建阶段提示词（Skill + 配置 + 章节事件 + RAG）
  → 生成
  → clean_stage_output（去掉多余解释）
  → ensure_stage_output_quality（规则校验）
  → 合格 → 写入工作区
  → 不合格 → 自修复（最多 2 次）
```

剧本阶段更特殊：多集剧本一次生成容易断章，所以**逐集生成**：

```
EP1 → 校验 → 落库 → EP2 → 校验 → 落库 → ...
某一集失败 → 回滚该集 → 询问用户确认修复
```

“已有集不会被静默覆盖”也是状态机约束：配置范围内集数都生成过了，就要求用户明确说“重写 EP2”。

## 流式协议：NDJSON

后端返回不是普通 JSON，而是每行一个事件的 NDJSON：

```
{"type":"start","data":{"phase":"preparing"}}
{"type":"message.delta","content":"正在写……"}
{"type":"done","content":"完成！","data":{...}}
{"type":"error","data":{"detail":"..."}}
```

前端 `utils/ndjsonStream.ts` 逐行解析。好处：

```
立即反馈（准备阶段就开始发事件）
事件可扩展（加字段不破坏协议）
错误事件化（不用等 HTTP 500）
```

## 并发控制：会话锁

同一个项目 + 用户同时发两条消息怎么办？

```python
lock = await acquire_session_lock(project_public_id, current_user_public_id)
async with lock:
    ...
```

会话级 asyncio 锁保证同一会话串行，不同会话互不阻塞。

## 面试怎么答“Agent 工作流怎么设计的”

> “我们没有把 Agent 当黑盒聊天，而是把创作流程建成状态机：配置确认、阶段前置检查、逐集生成、质量校验、自修复、回滚确认都落在会话状态里。配置和意图解析尽量用确定性规则，只有真正创作才调模型；流式协议用 NDJSON 事件，前端从准备到完成全程可见；会话锁保证同会话串行。”

这句话的潜台词：**我懂状态、懂并发、懂可观测性，而不只是会调 API**。
