# 项目全貌与架构地图

```

│   ├── app/
```

## 三层架构（和你旧笔记呼应）

你之前总结过三层世界：

```
Interface Layer   →  routers/（HTTP 入口）
Business Layer    →  services/（业务编排）+ tasks/（异步执行）
Infrastructure    →  core/、providers/、Redis、PostgreSQL、Chroma、OSS
```

AnonForge 严格遵守了它，并且多出两类“横切层”：

```
models/ + schemas/   →  数据契约（ORM 存全部，Schema 只给需要的）
core/config.py       →  全局配置
middlewares/         →  鉴权、耗时统计
```

## 业务域地图

| 域 | 后端关键文件 | 一句话职责 |
|---|---|---|
| 用户 | `services/user.py` | 注册登录、JWT、默认管理员 |
| 项目 | `services/project.py` | 项目 CRUD、成员、风格库、导演手册 |
| Provider | `services/provider.py` + `provider_runtime.py` | 多模型供应商接入与调用 |
| 小说 | `services/novel.py` + `novel_crawler.py` | 小说管理、导入、爬取、事件清洗 |
| 任务 | `core/tasks/` + `services/tasks.py` | 通用可靠异步任务系统 |
| 剧本创作 | `services/screenwriting/` | RAG + Agent 三阶段创作工作台 |
| 剧本管理 | `services/script.py` | 分集、正文 CRUD |
| 资产 | `services/asset.py` | 从剧本抽取角色/场景/道具 |
| 媒体 | `services/media.py` + `media_storage.py` | 图片/视频生成与存储统一入口 |
| 分镜 | `services/storyboard.py` | 分镜脚本生成与落库 |

## 一次完整请求的生命周期

```
浏览器
  │  POST /api/projects/{id}/novels/screenwriting/chat
  ▼
nginx/Vite 代理
  ▼
FastAPI（jwt_auth_middleware 校验 Token）
  ▼
routers/screenwriting.py（类视图）
  ▼
services/screenwriting/chat.py（业务编排）
  ├── 读取项目/会话/章节事件
  ├── RAG 准备（chroma + 混合检索）
  ├── 构建 Harness Agent（网关 + 工具 + 记忆）
  └── agent.stream_chat() → ProviderModelGateway → Provider → 大模型
  ▼
NDJSON 流式响应 → 前端逐行渲染
```

如果是媒体生成这类长任务，则不走同步链路，而是：

```
业务服务 → TaskJob/TaskItem 落库 → 入队 Redis Stream
         → Worker 抢占 → 调 Provider → 回写结果 → 前端轮询
```

## 面试怎么用

先画这张总图，再解释“哪些链路是同步的，哪些是异步的，为什么”。能说清同步/异步边界，就说明你真的理解系统，而不是背目录。
