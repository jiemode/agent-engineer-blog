# 通用异步任务引擎

## 为什么需要它

剧本生成要几分钟，视频生成要几十分钟。HTTP 请求不可能等这么久，所以：

```
同步链路：请求 → 直接调用 → 等结果 → 返回
异步链路：请求 → 落库 → 入队 → 立即返回 → Worker 慢慢跑 → 前端轮询
```

异步任务系统的核心问题不是“怎么跑”，而是“跑挂了怎么办”。

## 数据模型：Job / Item / DeadLetter

```
TaskJob（一个任务批次）
  └── TaskItem（一条可执行子任务，真正进队列的颗粒）
        └── TaskDeadLetter（重试耗尽后的死亡记录）
```

`TaskItem` 关键字段：

```
status          PENDING / QUEUED / RUNNING / SUCCEEDED / FAILED / CANCELLED / PARTIAL / PAUSED
payload         JSON 字符串（业务参数）
result          执行结果 JSON
worker_id       当前抢占的 Worker
attempt_count   已尝试次数
heartbeat_at    心跳时间
next_retry_at   下次重试时间
```

## 状态机

```
PENDING ──入队──▶ QUEUED ──Worker 抢占──▶ RUNNING ──成功──▶ SUCCEEDED
   │                  │                        │
   ▼                  ▼                        ▼
失败重试 ←──  重试次数耗尽 → FAILED（或写死信）
任意阶段          用户操作               CANCELLED / PAUSED
```

## 队列：Redis Stream + Consumer Group

为什么不用简单 List？

```
List（BRPOP）       一条消息只能被一个消费者拿走，谁拿走谁负责
Stream + Group     消费者组、PEL（Pending Entries List）、XAUTOCLAIM 认领
```

Stream 的 PEL 是灵魂：消息被消费但没 ACK 时留在 PEL 里，超时后可以被其他 Worker 认领。这让系统天然支持“处理到一半挂了也能恢复”。

## 抢占：CAS 语义

两个 Worker 同时读到同一条消息怎么办？

```python
# mark_task_item_running
UPDATE task_item
SET status='RUNNING', worker_id=?
WHERE public_id=? AND status IN ('PENDING','QUEUED')
```

只有状态匹配的那一个更新成功，另一个拿到 0 行更新，直接 ACK 丢弃。这就是数据库版的 Compare-And-Swap（CAS），是防重复执行的底牌。

## Worker 主循环

```
while True:
    定时跑一次 OrphanScavenger
    records = XREADGROUP 读一批（最多 4 条）
    for record in records:
        查 handler
        CAS 抢占（失败就 ACK 跳过）
        启动心跳协程（每 30s 刷新 heartbeat_at）
        执行 handler（带超时，默认 1 小时）
        成功 → 写 result → ACK
        失败 → 判断 retryable → 重试或死信 → ACK
```

并发用 `asyncio.Semaphore(max_concurrency)` 控制，防止一次拉起 1000 个协程。

## 失败与重试

`TaskHandlerFailure` 是业务主动抛出的失败，携带：

```
error_code      机器可读错误码
error_message   人类可读信息
result          诊断数据（写回任务子项，前端能看到）
retryable       False = 确定性失败，重试也没用
```

确定性失败直接 FAILED，不重试；可恢复失败按指数退避重试（默认最多 3 次）。

## 僵尸与孤儿：OrphanScavenger

Worker 崩溃后，RUNNING 任务会一直卡着。Scavenger 定期扫描：

```
1. 超过 stale_running_timeout 的 RUNNING → 重试或失败
2. PENDING 但没入队的 → 重新入队
3. Redis PEL 里滞留的消息 → XAUTOCLAIM 认领 → 根据数据库状态 ACK 或恢复
```

这解决的是分布式系统最常见的两类问题：

```
僵尸任务：标记 RUNNING 但没人执行
孤儿消息：队列里躺着但数据库状态对不上
```

## 优雅关闭

Worker 支持：

```
shutdown_timeout 内停止接收新任务
把 in-flight 任务跑完或标记失败
停掉心跳协程
```

## 业务方接入有多简单

每个业务模块只要：

```python
async def extract_assets_task(context):
    ...  # 真正的业务逻辑

ASYNC_TASKS = (
    AsyncTaskDefinition("asset.extract", extract_assets_task),
)
```

Engine 通过 `ASYNC_TASK_MODULES` 配置加载模块，扫描 `ASYNC_TASKS` 自动注册。业务代码不需要懂 Redis Stream 细节。

## 面试怎么答“自研任务队列 vs Celery”

> “我们用 Redis Stream + PostgreSQL 自研了通用任务引擎：数据库保存任务状态和结果，Stream 负责投递与消费者组，Worker 用 CAS 抢占防重复，心跳和 Scavenger 处理僵尸，重试耗尽进死信表。选自研是因为任务形态非常简单且需要和业务表强一致，Celery 的重型 broker/worker 语义反而带来额外运维复杂度。如果任务量再上一个量级，会考虑迁移到成熟队列或加分布式锁。”

记住三个关键词：**CAS 抢占、心跳、PEL 认领**。
